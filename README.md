# Бот поддержки канала «История Казахстана»

Telegram-бот для анонимной связи пользователей с администрацией канала **@historykazakhkz**:
приём обращений, ответы администратора свайпом, продажа тестов/конспектов/Premium,
приём заявок на сотрудничество, реквизиты и подтверждение оплат, финансовая и
обзорная статистика.

## Стек

Python 3.12 · aiogram 3 · PostgreSQL · SQLAlchemy 2 (async) · Alembic · Redis · Docker / Docker Compose.

## 1. Локальный запуск

1. Установите Python 3.12, PostgreSQL и Redis локально (или используйте `docker-compose up db redis`).
2. Скопируйте `.env.example` в `.env` и заполните:
   - `BOT_TOKEN` — токен бота от @BotFather;
   - `ADMIN_IDS` — Telegram ID администраторов через запятую;
   - `ADMIN_CHAT_ID` — ID административного чата/группы (см. раздел 4);
   - `DATABASE_URL`, `REDIS_URL` — под вашу локальную установку.
3. Создайте виртуальное окружение и установите зависимости:
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```
4. Примените миграции:
   ```bash
   alembic upgrade head
   ```
5. Запустите бота:
   ```bash
   python -m app.main
   ```
   По умолчанию (пустой `WEBHOOK_URL`) бот работает в режиме long polling.

## 2. Запуск на сервере (Docker)

1. На сервере склонируйте проект и создайте `.env` (см. `.env.example`), заполнив реальные
   значения `POSTGRES_*`, `DATABASE_URL` (host должен быть `db`, как в docker-compose),
   `REDIS_URL=redis://redis:6379/0`, `BOT_TOKEN`, `ADMIN_IDS`, `ADMIN_CHAT_ID`.
2. Соберите и запустите:
   ```bash
   docker compose up -d --build
   ```
   Сервис `migrate` автоматически применит миграции перед стартом `bot`.
3. Логи:
   ```bash
   docker compose logs -f bot
   ```
4. Для режима webhook заполните `WEBHOOK_URL` (домен с HTTPS, например
   `https://your-domain.example`) и `WEBHOOK_PATH` — бот поднимет aiohttp-сервер на
   `WEBAPP_HOST:WEBAPP_PORT` (проброшен наружу как `8080` в `docker-compose.yml`); настройте
   реверс-прокси (nginx/traefik) с TLS перед этим портом. Если `WEBHOOK_URL` пуст — бот
   работает в режиме long polling, и порт можно не пробрасывать.

### Резервное копирование БД

```bash
docker compose exec db pg_dump -U $POSTGRES_USER $POSTGRES_DB > backups/backup_$(date +%F).sql
```
Настройте эту команду в cron на сервере (например, ежедневно ночью).

## 3. Добавление администраторов

Отредактируйте `ADMIN_IDS` в `.env` (через запятую, без пробелов обязательных, но лучше
без пробелов) и перезапустите бота:
```bash
docker compose restart bot
```
Только перечисленные ID получают доступ к административным командам и могут отвечать
в административном чате.

## 4. Создание административного чата

1. Создайте приватную группу в Telegram (например, «Поддержка — История Казахстана»).
2. Добавьте бота в группу и назначьте его администратором группы (нужно для корректной
   пересылки файлов и работы с сообщениями).
3. Узнайте ID группы: отправьте в группу любое сообщение и перешлите боту @userinfobot,
   либо временно включите логирование апдейтов — ID группы отрицательный, например
   `-1001234567890`.
4. Впишите этот ID в `ADMIN_CHAT_ID` в `.env` и перезапустите бота.

Все обращения пользователей будут приходить в эту группу; администраторы отвечают
свайпом (Reply) прямо на сообщение конкретного пользователя.

## 5. Настройка реквизитов для покупок

В административном чате отправьте команду:
```
/payment_settings
```
Выберите «Реквизиты для покупок» и заполните по очереди: банк, получателя, номер
телефона/карты, основной текст сообщения (поддерживает `{amount}`, `{recipient}`,
`{bank}`, `{requisites}`), текст после оплаты, при необходимости — фото с реквизитами.
Нажмите «Предпросмотр», чтобы проверить итоговое сообщение перед сохранением.
Изменения применяются сразу, без перезапуска бота.

## 6. Настройка реквизитов для сотрудничества

Там же: `/payment_settings` → «Реквизиты для сотрудничества» — отдельные банк, получатель,
номер, текст и фото/QR, независимые от реквизитов для покупок. Можно указать те же данные,
что и для покупок, либо полностью отдельные.

## 7. Подтверждение и отмена оплат

- Когда пользователь присылает чек, под ним в административном чате появляются кнопки
  «Оплата подтверждена», «Отклонить чек», «Запросить новый чек».
- «Оплата подтверждена» → бот просит проверить сумму → «Подтвердить сумму и оплату» —
  только после этого шага сумма попадает в статистику доходов (идемпотентно: повторное
  нажатие или подтверждение вторым администратором не задваивает сумму — см.
  `app/services/payments.py::confirm_payment` и тесты в `tests/test_payments_idempotency.py`).
- Ошибочно подтверждённую оплату можно отменить командой:
  ```
  /cancel_payment ID_оплаты
  ```
  Бот запросит причину отмены; запись сохраняется в БД со статусом «Оплата отменена» и
  вычитается из статистики, но не удаляется.

## 8. Финансовая статистика

```
/finance            — выбор периода кнопками
/finance_today
/finance_week
/finance_month
/finance_all
```
Показывает подтверждённые оплаты по категориям (тесты, Premium, конспекты, всё
вышеперечисленное, сотрудничество), суммарно по покупкам, по сотрудничеству и общий оборот.
Периоды считаются по таймзоне `Asia/Aqtobe` (настраивается через `TIMEZONE` в `.env`).

## 9. Статистика обращений

```
/stats
/stats_today / /stats_week / /stats_month / /stats_all
```
Количество обращений, уникальных/новых/повторных пользователей, отвечено/без ответа/закрыто,
разбивка по причинам и подкатегориям покупок, конверсия покупок в оплату.

## 10. Выгрузка отчётов

```
/report              — обращения + доходы одним отчётом за период
/export_report        — выгрузка подтверждённых оплат за период в CSV или Excel
```

## Обработка ошибок и журналирование

- Все ключевые действия (новое обращение, ответ администратора, отправка реквизитов,
  получение чека, подтверждение/отмена оплаты, закрытие обращения) можно расширить записью
  в таблицу `audit_log` (модель уже создана в `app/db/models.py`; вызовы логирования
  добавляются по мере необходимости в соответствующих хендлерах).
- Общий лог приложения пишется в stdout и в файл `bot.log` (см. `app/logging_conf.py`).
- Отправка сообщений пользователю обёрнута в `services/queue.send_with_retry`: временные
  сетевые ошибки и `Too Many Requests` обрабатываются автоматически повторной отправкой;
  блокировка бота пользователем (`TelegramForbiddenError`) отдельно перехватывается и
  админу показывается «Сообщение не доставлено...».

## Идемпотентность оплат (защита от двойного учёта)

- Подтверждение оплаты выполняется в транзакции с блокировкой строки (`SELECT ... FOR UPDATE`
  на PostgreSQL) и флагом `counted_in_revenue`. Повторное нажатие кнопки или параллельное
  подтверждение двумя администраторами не увеличивает доход дважды — см.
  `app/services/payments.py::confirm_payment`.
- Проверяется тестами:
  ```bash
  pytest tests/test_payments_idempotency.py -v
  ```

## Тесты

```bash
pip install -r requirements.txt
pytest -v
```
Тесты используют изолированную in-memory SQLite базу (см. `tests/conftest.py`) и покрывают:
- атомарную последовательную нумерацию обращений (`tests/test_ticket_flow.py`);
- защиту от двойного учёта оплаты при повторном/параллельном подтверждении и корректную
  отмену подтверждённой оплаты (`tests/test_payments_idempotency.py`).

## Работа с миграциями

Начальная миграция (`alembic/versions/0001_initial.py`) создаёт схему прямо из моделей
SQLAlchemy (`Base.metadata`), чтобы исключить расхождение между кодом и БД на старте проекта.
Для последующих изменений схемы используйте обычный процесс Alembic:
```bash
alembic revision --autogenerate -m "описание изменения"
alembic upgrade head
```

## Основные пользовательские сценарии (проверено вручную по коду)

1. `/start` → приветствие с username/именем → выбор причины обращения.
2. Причина «Покупка» → выбор подкатегории → создание обращения → сообщение о том, что
   можно писать вопрос.
3. Любое сообщение до выбора причины удаляется/игнорируется, показывается напоминание и
   кнопки заново.
4. Свободное сообщение (текст/фото/видео/документ/голос/видеосообщение/аудио/стикер)
   после выбора причины пересылается в административный чат с информационным блоком-цитатой
   и клавиатурой действий, привязанной к обращению.
5. После получения реквизитов пользователь может нажать «Я оплатил — отправить чек» и
   прислать фото/документ с чеком; текст вместо файла отклоняется с просьбой прислать файл.
6. `/new` при открытом обращении спрашивает подтверждение перед созданием нового.

## Основные администраторские сценарии

1. Ответ свайпом (Reply) на пересланное сообщение пользователя — уходит только этому
   пользователю, от имени бота, с заголовком «Ответ администратора:»; работает даже для
   очень старых сообщений, так как связь хранится в PostgreSQL.
2. Ответ не на сообщение пользователя → бот сообщает, что получателя определить не удалось.
3. Кнопка «Отправить реквизиты» / «Отправить реквизиты для сотрудничества» → ввод суммы →
   предпросмотр → «Отправить пользователю» (только на этом шаге реквизиты уходят пользователю).
4. Получение чека → «Оплата подтверждена» → проверка/правка суммы → «Подтвердить сумму и
   оплату» → сумма попадает в доход, статус обращения меняется на «Оплачено».
5. `/finance`, `/stats`, `/report`, `/export_report`, `/history`, `/user`, `/cancel_payment`.

## Безопасность

- Все административные хендлеры защищены двойным фильтром: `IsAdminChat` (апдейт из
  сконфигурированного чата) и `IsAdmin` (Telegram ID отправителя — в списке `ADMIN_IDS`).
- Callback-данные всегда проверяются против БД (например, существование обращения/оплаты)
  перед выполнением действия — идентификаторы из кнопок не считаются доверенными сами по себе.
- Токен и секреты хранятся только в `.env` (файл в `.gitignore`, не коммитится).
- Пользователю никогда не показываются технические детали ошибок и данные администратора.
- Подтверждение оплаты идемпотентно на уровне БД (см. выше) — исключает двойной учёт при
  гонке двух администраторов.

## Ограничения текущей реализации / что можно развить дальше

- Пагинация истории (`/history`) сейчас показывает последние N обращений одним выводом;
  кнопки «Назад/Далее» из ТЗ можно добавить, расширив `handlers/admin/history.py` — модели
  и данные для этого уже готовы.
- Запись в `audit_log` подготовлена (модель есть), но вызывается не из каждого действия —
  расширяется по необходимости.
- Полный набор редактируемых настроек `/payment_settings` (все поля) реализован; тексты по
  умолчанию заданы в `services/payments.py` и переопределяются через `/payment_settings`.
